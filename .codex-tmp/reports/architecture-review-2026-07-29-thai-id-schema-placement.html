Problem

Identity is duplicated in three modules whose implementations own different facts: Firebase imports, mobile screening records, and clinical visits.

Solution

A deep patient registry module owns person identity, source mappings, card versions, matching, and conflicts behind one interface.

Benefits

  • • locality: identity rules concentrate
  • • leverage: one match interface
  • • patient UID stops leaking
  • • private card-photo adapter

After scanner writes

The scanner becomes another source with different freshness, card fields, authorization, and conflict rules hidden inside a mirror interface.

Problem

Both tables use Firebase text IDs as primary keys and allow duplicate Thai IDs; neither owns verified card identity.

Solution

Do not add scanner writes. Keep these as adapters or projections at the registry seam.

Benefits

  • • preserves mirror semantics
  • • avoids silent overwrite
  • • conflict rules stay local
  • • migration remains replayable
