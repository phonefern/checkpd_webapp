Problem

Identity leaks across mirror rows and visit rows; none provides one stable interface for a person read from a card.

Solution

One deep patient identity module owns normalized Thai ID and verified card demographics; visits reference its patient_uid.

  • • locality: identity rules concentrate
  • • leverage: one upsert interface
  • • tests cross one seam
  • • mirrors remain adapters

public.users: Firebase-backed mirror identity
checkpd.users: reporting/migration mirror
core.patients_v2: repeatable visit row
pd_screenings: absent live

Problem

Each existing interface carries a different invariant; direct writes couple scanner behaviour to migration or visit semantics.

Solution

Do not choose among them as scanner authority; keep them downstream adapters or visit consumers.

  • • avoids mirror corruption
  • • preserves visit invariants
  • • no missing-table dependency
  • • seam remains explicit

Recommended stored shape

core.patient_identities

patient_uid primary key; normalized thaiid unique; names, DOB, gender, ID-card address; verified timestamps.

core.thai_id_cards

Card issuer, issue/expiry dates, optional private photo path, last scan actor/time. No base64 photo column.

core.thai_id_scan_events

Optional append-only audit: patient UID, actor, result, reader version, timestamp. No repeated raw payload.

Photo stays temporary by default. If retention is approved, store it in a private Supabase Storage bucket and keep only its path in Postgres.

Top recommendation

Deepen patient identity in core.patient_identities

Thai ID card data describes a person, not a screening visit or a Firebase mirror; one identity interface gives the scanner, QA visits, exports, and future matching the most leverage and locality.
